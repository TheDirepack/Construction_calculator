# PDF editor and conduit workflows

The editor should work in both directions. A crew can trace a route on a plan and turn it into a project run, or open an existing run and generate a diagram or place the route back on a sheet. A route used in several similar rooms becomes a reusable layout. Each placement can be checked and adjusted before it becomes a separate run.

## From a PDF to a conduit run

1. **Choose and calibrate a zone.** Draw the boundary around the plan or detail. Choose a preset or enter known dimensions with the shared calculator. Use independent references to verify the correction. Show which zone applies to each leg and have the user split a leg crossing a zone boundary. An unscaled drawing can hold pins, notes, and counts. [Zone calibration implementation plan](../plans/pdf-zone-calibration.md)
2. **Place the route points.** Choose start and end equipment, then tap the intermediate points. Offer pull boxes, conduit bodies, risers, drops, and sheet or floor transitions as named points. A magnifier and horizontal or vertical locking are the first precision aids. Vector endpoint, midpoint, and on-line snapping can follow. Save raw and snapped positions when useful for undo or review. Comparable measurement tools use explicit calibration, viewport scales, and vector snapping. [Bluebeam measurement tools](https://support.bluebeam.com/online-help/revu20/Content/RevuHelp/Menus/Window/Panels/Measurements/Measure-Tab--MV.htm) · [Bluebeam viewports](https://support.bluebeam.com/online-help/revu20/Content/RevuHelp/Menus/Window/Panels/Measurements/Defining-Multiple-Scale-Viewports.htm)
3. **Resolve the path.** List plan distances and allow entered elevations, slopes, and field lengths. For instance, a 12 ft plan leg with a 5 ft rise over the same leg is a 13 ft sloped straight. If the 5 ft rise is a separate vertical leg, it contributes its own 5 ft and needs its own bend transitions. Require the user to connect matching continuation points across sheets and confirm what a plan corner represents.
4. **Review the bends and developed length.** A turn in the trace is a bend candidate. Ask for bend plane and radius or a fitting selection. For two straight centerlines meeting at a virtual corner, a circular bend of angle θ and radius R trims `R × tan(θ/2)` from each adjacent straight and adds the arc `R × θ` with θ in radians. Only apply that model when the trace represents the intersecting tangents. For a traced arc or entered tangent-to-tangent length, use its confirmed endpoints to avoid double-counting. Check that adjacent bend trims fit within each straight. A return or compound offset can be entered using the existing bend tools and then placed against the trace.
5. **Save a new run or review an update.** Show measured portions, field inputs, unresolved sections, developed length, and where each pull section begins and ends. Keep a draft until required route details are resolved. Pass the accepted path through `Project.withRunPath`. That keeps the raceway length synchronized for Voltage Drop, wire footage, and the Wire Pull Planner. Keep the source sheet link on the run and the run link on the drawing. [Run path and update model](../../core/model/src/main/kotlin/com/thedirepack/constructioncalc/core/model/RunPath.kt)

## From a conduit run to a PDF

- **Generate an installation sheet from any run.** Draw an ordered schematic with start/end equipment, straight lengths and slopes, bend numbers and radii, pull points, and section totals. Include the bend marks available from Conduit Bending, an elevation view when the supplied geometry supports one, and a summary from the existing pull and material calculations. Label diagrams as schematic when the run lacks spatial placement. Generate the sheet using the app's existing report approach and share it independently or append it to an annotated plan.
- **Show a linked route on its drawing.** If the run came from a trace, render its accepted geometry on the original sheet and show numbered points, direction arrows, rise/drop symbols, and paired off-sheet references. Let the user choose which labels, measurements, and layers are visible in the export. A run with no drawing link starts as a placement draft. The user chooses a start and heading, supplies any missing turn directions, and confirms tie-in points and the sheet scale. A preview shows mismatches between the installed run and the proposed placement.
- **Keep the view and the calculations in sync.** The current model stores each straight's length and slope, a bend's angle, radius and plane, and pull points. It lacks placement, azimuth, and left/right turns. Two runs with equivalent pull inputs can therefore have different footprints. Store page anchors, explicit turn directions where needed, and links between trace spans and accepted path sections. Keep that spatial data with the drawing placement so the existing model remains the input to electrical calculations. Detect edits against the accepted route revision and ask the user to review changed span links before redrawing a placement. [Current run model](../../core/model/src/main/kotlin/com/thedirepack/constructioncalc/core/model/RunPath.kt)

## Duplicate or transfer a layout

- **Rigid copy for a repeated room.** Pick a source route, target sheet, anchor, and heading or matching pair of reference points. Translate and rotate in real-world units, then project onto the target scale. A route drawn at a different paper scale should keep its real dimensions. Show a ghost preview with endpoint and helper-point positions. Offer mirroring separately, with a preview of the changed turn directions and explicit confirmation at equipment and pull points.
- **Copy and adapt for a different room.** Copy the source's point sequence, labels, and selected settings into a draft, then let the user move anchors or retrace a leg. Recompute distances and bend candidates where geometry changes. Flag remaining constraints, such as a pull box location or a riser whose height still needs to be entered. A choice to remember pull or conduit settings is independent of copying circuit assignments.
- **Start from a PDF someone sent.** When a source drawing contains a line or polyline annotation, offer its vertices as a route draft after the user selects it. For vector page content, start with a selected stroke and let the user confirm connected spans one at a time. A scanned or flattened plan starts with manual tracing. Each case still needs a checked scale and user-supplied elevations and fittings. A visible line alone may represent a home run arrow, a symbolic route, or another trade's work. [PDFBox page annotations and geometry](https://pdfbox.apache.org/docs/2.0.8/javadocs/org/apache/pdfbox/pdmodel/PDPage.html) · [PDFBox annotation markup](https://pdfbox.apache.org/docs/2.0.11/javadocs/org/apache/pdfbox/pdmodel/interactive/annotation/PDAnnotationMarkup.html)
- **Create an independent run.** Give the new run and copied items new IDs. Remap bend source-item IDs if those items were copied, and recalculate results for the new route. Ask the user to assign destination equipment and circuits. A change to the copy should leave the source route and its calculations intact. The existing project duplication already demonstrates how to remap bend source IDs when copied items receive fresh IDs. [Project duplication](../../core/model/src/main/kotlin/com/thedirepack/constructioncalc/core/model/Project.kt#L124)
- **Transfer to a revised drawing.** Choose corresponding landmarks, preview rotation, translation and scale, and check additional control points before offering a transfer. Keep the old revision and its accepted route history. Flag missing landmarks, changed equipment and mismatched scale. A visual overlay may use a different transform from a measured route if the scan is distorted. Existing plan tools use multiple matching points for register-and-compare workflows. [Bluebeam revision alignment](https://support.bluebeam.com/revu/features/align-pdfs-with-overlay-pages.html)

## Feature research for the rest of the editor

| Feature | Implementation direction and first check |
|---|---|
| Project drawings and viewer | Use Android's file picker, store originals offline by revision, and add thumbnails, page labels, rotation, bookmarks and a jump-to-page action. Start with tiled `PdfRenderer` at API 26. Compare Jetpack PDF for search, accessibility and live overlays on supported devices. Test a 90° page, nonzero crop origin, and a large sheet. [Tooling research](pdf-tooling.md) |
| Calibration and takeoff | Store known distances, calibration points, scale, verification state, and page or region IDs. Compute distances and angles from the points, areas from closed polygons, and counts by item group. Recalibration refreshes measured quantities. An explicitly dimensioned shape keeps the entered dimensions and changes its drawn size. Publish compatible quantities to the calculator picker and keep the drawing provenance. [FieldScale measurements](fieldscale.md#6-how-measurement-is-implemented) |
| Markups and reusable symbols | Start with text, arrows, lines, highlights, dimensions, rectangles, then add clouds, ink, project equipment tags, layer visibility, undo/redo and reusable templates. Keep the shapes editable in the project. Place a template in real units when it carries a fixed size. Use reviewable lists for counts and quantities, with jump-to-sheet links and CSV export for schedules and estimating. ## Prototype order and checks

The reference geometry passed in a desktop scratch check. A 12 ft plan leg with a 5 ft rise measured 13 ft along the slope. Two straight centerlines of 10 ft and 8 ft meeting at 90° produced about 17.57 ft of developed length with a 1 ft centerline radius. The check flagged a 1.5 ft leg between two such bends as too short for both trims. A route copied to a rotated sheet at half the drawing scale kept the same real leg lengths. These checks covered the math before Android integration.

1. Open and calibrate two sheets, then put down route points and publish one measured length to the app's picker. Verify the resulting endpoints through zoom, rotation, and reopening on API 26.
2. Trace a plan leg, add a vertical transition and a pull point, then accept a run. Compare the expected developed length and pull sections with the calculator output. Include a fixture where the bend trims cannot fit.
3. Generate a schematic for an unplaced legacy run, then place a fully specified route on a sheet. Duplicate that placement on a rotated, differently scaled destination and verify the same real lengths. Change one destination leg and confirm the source is untouched and the new run has independent links.
4. Export a marked PDF using PDFBox, inspect it in an independent reader, restore editable data from JSON, and restore a two-drawing project ZIP. Flag a revised drawing for re-review. Run the same checks against whichever Jetpack edit functions are available on the test device.

PDFBox is a practical first candidate for writing and vector inspection, as in [the FieldScale findings](pdf-tooling.md#what-fieldscale-does-on-android). Before choosing the published Android port for the app, check parser maintenance, memory use on large sheets, and release builds. Keep render, edit, and export implementations behind small interfaces so the same project data works with the Android framework renderer and any supported Jetpack capabilities.
